# 推荐引擎字段定义与接口草案

## 1. 文档目的

本文用于明确 MVP 阶段推荐引擎的数据输入、输出、核心字段、评分思路与接口草案，方便前后端并行开发。

适用范围：
- 表单输入数据结构
- 候选目的地配置数据结构
- 推荐结果输出结构
- 推荐接口草案
- 换一批逻辑建议

---

## 2. 推荐引擎设计原则

MVP 阶段采用：

> 结构化规则 + 候选池配置 + 评分排序

不做复杂 AI 决策。

核心原则：
1. 先过滤，再排序
2. 结果必须可解释
3. 文案和推荐逻辑尽量配置化
4. 结果需支持“换一批”
5. 避免输出 3 个过度相似的目的地

---

## 3. 用户输入字段定义

推荐请求由前端表单提交，建议字段如下。

## 3.1 Request Schema

```json
{
  "departureCity": "shanghai",
  "companion": "couple",
  "budgetLevel": "mid",
  "travelPreference": "citywalk",
  "transportTolerance": "train_or_flight",
  "crowdSensitivity": "avoid_if_possible",
  "refreshSeed": 0
}
```

## 3.2 字段说明

### departureCity
出发城市。

可选值：
- `beijing`
- `shanghai`
- `guangzhou`
- `shenzhen`

### companion
同行人。

可选值：
- `solo`
- `couple`
- `friends`
- `family_kids`
- `parents`

### budgetLevel
预算档位。

可选值：
- `budget`
- `mid`
- `comfort`

### travelPreference
旅行偏好。

可选值：
- `food`
- `nature`
- `seaside`
- `citywalk`
- `niche`

### transportTolerance
交通接受度。

可选值：
- `train_3h`
- `train_or_flight`
- `worth_longer`

### crowdSensitivity
人流敏感度。

可选值：
- `very_sensitive`
- `avoid_if_possible`
- `not_sensitive`

### refreshSeed
用于“换一批”时生成不同结果。
- 初始值建议为 `0`
- 用户每点击一次“换一批”，前端 +1 再请求一次

## 4.2 关键字段说明

### 基础标识字段
- `id`: 英文唯一 ID
- `name`: 目的地中文名
- `region`: 所属区域/省份
- `categories`: 用于 UI 标签或去重分类

### 适配标签字段
- `departure_fit`: 不同出发城市适配度，1~5 分
- `trip_length_fit`: 适合的出行天数
- `budget_fit`: 适合的预算档位
- `companions_fit`: 适合的同行人类型
- `preferences_fit`: 适合的偏好类型
- `transport_fit`: 适合的交通接受度
- `crowd_sensitivity_fit`: 适合的人流敏感度

### 评分字段
建议采用 1~5 分，`fatigue_score` 为负向指标，值越高表示越折腾。

- `duanwu_fit_score`
- `avoid_crowd_score`
- `accessibility_score`
- `people_fit_score`
- `budget_score`
- `fatigue_score`

### 文案字段
用于结果页直接展示，减少前端拼接复杂度。

- `reason_short`
- `reason_duanwu`
- `reason_avoid_crowd`
- `risk_tip`
- `alternatives`

## 5.2 budgetLevel 映射
- `budget` -> `省钱型`
- `mid` -> `适中`
- `comfort` -> `可以稍微住好一点`

## 5.3 travelPreference 映射
- `food` -> `轻松逛吃`
- `nature` -> `自然放空`

- `citywalk` -> `城市漫游`

## 6. 推荐流程草案

## 6.1 Step 1: 过滤

过滤条件建议：

1. `departure_fit[departureCity] < 2` 时可直接过滤
2. 如果用户选择 `train_3h`，则过滤掉 `transport_fit` 不包含 `尽量高铁 3 小时内` 的目的地
3. 如果用户选择 `very_sensitive`，优先过滤 `avoid_crowd_score < 3.5` 的目的地
4. 如果用户选择特定偏好，优先过滤 `preferences_fit` 完全不匹配的目的地
5. 如果用户选择特定同行人，优先过滤 `companions_fit` 不匹配的目的地

说明：
- MVP 可适当保留“软过滤”，避免结果为空
- 如果过滤后少于 5 个候选，可降级为弱过滤，仅降低权重

---

## 6.2 Step 2: 综合打分

建议初始公式：

```text
score =
  duanwu_fit_score * 0.25 +
  avoid_crowd_score * 0.25 +
  departure_fit_score * 0.20 +
  preference_match_score * 0.10 +
  companion_match_score * 0.08 +
  budget_match_score * 0.07 +
  transport_match_score * 0.05 -
  fatigue_score * 0.10
```

说明：
- `departure_fit_score` 来自 `departure_fit[departureCity]`
- `preference_match_score` 可简单设为：匹配=5，不匹配=2
- `companion_match_score` 可简单设为：匹配=5，不匹配=2
- `budget_match_score` 可简单设为：匹配=5，不匹配=3
- `transport_match_score` 可简单设为：匹配=5，不匹配=2

该公式仅作为 MVP 起始版本，后续可根据投放反馈调参。

---

## 6.3 Step 3: 排序与去重

排序后取前 N 个候选，再做去重。

### 去重策略建议
如果前 3 个候选：
- `categories` 过度相似
- 且 `region` 也相近

则尝试从第 4、5 名中补一个风格更不同的结果。

目标：
- 避免 3 个推荐都是“同类型美食小城”
- 尽量让结果具备选择感

---

## 6.4 Step 4: 换一批

“换一批”不建议完全随机，建议采用：

1. 前端 `refreshSeed + 1`
2. 后端在 Top 8 候选中做轻微扰动
3. 保留强相关候选，替换掉边缘位

简单实现方式：
- 每次请求根据 `refreshSeed` 对候选排序加一个微小偏移值
- 或者输出 `rank 1-3`, `rank 2-4`, `rank 3-5` 这种滑动窗口式结果

要求：
- 不能和上一批完全一样
- 也不要偏离太远，避免结果失真

## 8. 接口草案

## 8.1 获取推荐结果

### Endpoint
`POST /api/recommendations`

### Request Body
见第 3 节 Request Schema。

### Response
见第 7 节 Response Schema。

### 说明
- 推荐结果由后端统一生成
- 前端只负责表单提交和结果展示
- 推荐文案优先由配置项提供，不在前端做复杂拼接

---

## 8.2 获取候选目的地配置（可选）

### Endpoint
`GET /api/destinations`

### 用途
- 调试或后台预览使用
- 正式用户态不一定需要暴露

### Response
返回当前候选池列表或简版数据

---

## 8.3 提交用户反馈

### Endpoint
`POST /api/feedback`

### Request Schema

```json
{
  "requestId": "rec_20260602_001",
  "helpful": true,
  "selectedDestinationId": "quanzhou",
  "comment": "更想看适合深圳出发的海边推荐"
}
```

### 字段说明
- `requestId`: 对应一次推荐请求
- `helpful`: 是否有帮助
- `selectedDestinationId`: 用户最感兴趣的目的地，可为空
- `comment`: 选填

## 9. 前后端协作建议

### 前端负责
- 首页与表单交互
- 结果页展示
- “换一批”与“修改条件”交互
- 反馈提交流程

### 后端负责
- 候选池数据维护
- 字段映射处理
- 推荐过滤与打分
- 推荐结果生成
- 反馈记录

---

## 10. MVP 实现建议

如果时间非常紧，可采用最低成本方案：

1. 候选池先用本地 JSON 文件维护
2. 后端接口只做 3 个：
   - `/api/recommendations`
   - `/api/feedback`
   - `/api/health`（可选）
3. 推荐逻辑先写成一个纯函数模块，方便后续迁移
4. 分数与过滤阈值统一抽到配置常量中
